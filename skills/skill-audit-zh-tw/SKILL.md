## 這個 skill 幫你做什麼

拿一個寫好的 SKILL.md，對照 7 條標準一項一項檢查，告訴你哪裡通過、哪裡不通過、要怎麼改。

不幫你重寫整個 skill。只做審查：量數字、對清單、指出問題、給修正方向。改完之後，再跑一次審查，直到 7 項都通過。

適用對象：剛寫好的 skill、接手別人寫的 skill、放了一陣子想拿出來更新的 skill。

## 審查前先準備

審查之前，先把東西備齊，不要邊審邊找：

1. **目標 skill 的完整檔案**：SKILL.md 本體，加上它引用的所有 reference 檔案。先列一張清單：主檔 1 個，reference 有幾個、各叫什麼。
2. **量測工具**：終端機裡的 `wc -l`（算行數）和 `grep '^#'`（列出標題）。沒有終端機，用編輯器的行數顯示也行，重點是數字要量出來，不是憑感覺。
3. **測試用的任務**：挑一個這個 skill 最常用的真實任務，等一下第 ③ 項要用。不要用假想任務。
4. **預期搭配的模型**：這個 skill 是給哪個模型用的？Claude Code 預設是 Sonnet，但如果你的使用者也會用 Haiku 或 Opus，審查時就要三個都測。

## 七項檢查：怎麼量、怎麼判、怎麼改

每一項都有三件事：怎麼量（數字怎麼來）、通過標準（怎樣算過關）、不通過怎麼改（具體改法）。

### ① 長檔案有目錄

**怎麼量：**

- 對 SKILL.md 和每一個 reference 檔案跑 `wc -l`，記下行數。
- 超過 100 行的檔案，檢查最上方有沒有 content list。
- 把 content list 的每一項拿去跟檔案裡的標題對照：`grep '^#' 檔案` 列出所有標題，一項一項對。

**通過標準：**

- 超過 100 行的檔案，最上方有 content list。
- content list 的名稱跟段落標題一字不差。標題改了，目錄也要跟著改。
- 100 行以下的短檔，不用硬加目錄。短檔加目錄是多餘的。

**不通過怎麼改：**

- 沒有目錄：篩出超過 100 行的檔案，在最上方加入 content list，列出各節標題。
- 目錄對不上標題：先改標題或先改目錄，兩邊統一。不要留一個過期的目錄，比沒有目錄更糟。
- 檔案超過 500 行：先拆，不要只加目錄。目錄救不了過長的檔案，見第 ④ 項。

### ② 自由度有分層

**怎麼量：**

- 把 skill 裡的每一個步驟攤開，問三個問題：這一步的「做法」能不能變？「順序」能不能換？「結果」錯了會有什麼後果？
- 依答案分進三格：高自由度、中自由度、低自由度。

| 自由度 | 形式 | 判斷方法 |
|---|---|---|
| 高 | 純文字目標 | 做法可變，結果由模型判斷；錯了可以重來，後果輕 |
| 中 | 可調整的 template | 結構固定，留幾個選項；錯了要花時間重做，後果中等 |
| 低 | 固定 script | 順序與參數嚴格受控；錯了會刪資料、會花錢、會發錯東西，後果重 |

**通過標準：**

- 每個步驟都標得出自由度。標不出來，表示這一步寫得含糊。
- 高風險步驟（刪資料、發送、付款、對外發布）是低自由度，有固定 script 或固定操作順序。
- 低風險步驟（寫草稿、整理、發想）是高自由度，沒有綁死做法。
- 同一個 skill 裡可以混用：不同步驟用不同自由度。

**不通過怎麼改：**

- 高風險步驟只用文字描述：「刪除前請確認」不夠。改成固定 script，或寫死操作順序，一步一步照著做。
- 低風險步驟綁太死：把「一定要照這五步」改成「目標是這個，做法可以換」。
- 檢查一句話：低自由度通常需要 script，而非更多文字。文字寫得再長，也代替不了固定 script。

### ③ 逐個模型測試

**怎麼量：**

- 用審查前準備好的那個真實任務，依序在 Haiku、Opus、Sonnet 上跑一次。
- 每次記錄三件事：有沒有漏步驟、有沒有多做不需要的事、結果能不能直接用。

**通過標準：**

- Haiku：引導夠不夠。沒漏步驟，任務完整達成。
- Opus：沒有過度解釋。比較「有 skill」和「沒 skill」的結果，有 skill 的比較好。
- Sonnet：指令清楚，結果有效率。讀得懂、做得完。
- 三個模型都通過，才算通過。只測一個不算。
- SKILL.md 的 YAML front matter 註明預期搭配的模型。

**不通過怎麼改：**

- Haiku 漏步驟：把漏掉的那一步寫清楚，或改用 script。不要只加更多文字，加了還是漏，就改成 script。
- Opus 過度解釋：逐步刪減指令再測。刪一小段，測一次，找到剛好的量。
- 有 skill 反而比沒 skill 差：先刪，再測。刪到比沒 skill 好為止。
- 三個模型測完，把結果寫進 front matter 或 skill 末尾：預期搭配哪個模型、哪個模型表現怎樣。

### ④ References 只放一層

**怎麼量：**

- 從 SKILL.md 出發，畫出引用關係：主檔連到哪些 reference？那些 reference 有沒有再連到別的檔案？
- 量主檔行數：`wc -l SKILL.md`。

**通過標準：**

- 每份 reference 都能從主檔直達。沒有「主檔 → A 檔案 → B 檔案」這種兩層跳轉。
- SKILL.md 主體在 500 行以內，作為入口與目錄。
- 檔案依領域或客戶拆分，需要時才載入。不是全部塞進主檔。

**不通過怎麼改：**

- 有兩層跳轉：把底層檔案的連結拉到主檔。底層檔案可能只被預覽，關鍵內容容易漏讀。
- 主檔超過 500 行：拆成主檔＋reference。主檔留入口、判斷邏輯、目錄；細節搬到 reference。
- 拆分原則：依領域或客戶拆，不要依「重要／不重要」拆。需要時才載入。

### ⑤ Checklist 能阻止跳步

**怎麼量：**

- 找出 skill 裡所有的 checklist，一條一條問：這份清單的「順序」有沒有重要到非照著做不可？
- 檢查每一份 checklist 有沒有寫「失敗時回到哪一步」。

**通過標準：**

- 順序真的有重要的步驟，才用 checklist。順序不重要就不要用，列出階段目標就好。
- 每一份 checklist 都寫清楚：失敗時回到哪一步。沒寫回返路徑的 checklist，擋不住跳步。
- 驗證通過，才算完成。清單上寫了「驗證」這一項，而且有具體的驗證方法。

**不通過怎麼改：**

- 順序不重要卻用了 checklist：改成階段目標清單，讓模型自己判斷順序。
- 沒有回返路徑：補上。格式就是一句話：「第 4 步引用不完整 → 回到第 3 步」。
- 有 checklist 但沒有驗證項：最後加一項驗證，寫清楚怎麼驗、怎樣算通過。

### ⑥ 自我修正循環

**怎麼量：**

- 檢查 skill 裡有沒有「寫完之後再檢查一遍」的步驟。具體看三件事：有沒有對照的規範文件（style guide 或 brand voice）、有沒有標註問題的方法、有沒有「不通過就回去改」的迴圈。

**通過標準：**

- 流程是四步：起草 → 對照規範審查 → 標註問題並修訂 → 再次審查。未通過回到修訂，通過才定稿。
- 標註問題時，要指出問題和違反的規範段落。只說「這裡不好」不算。
- 檢查可以是文字規範，不一定是程式碼。文字規範也算檢查。
- 規則改善有門檻：發現規範沒涵蓋的問題，可以建議新規則，但使用者核准後才寫入文件。

**不通過怎麼改：**

- 沒有審查步驟：補上四步循環。寫完就直接定稿，很容易留下沒發現的問題。
- 審查沒有對照文件：指定一份規範文件（style guide 或 brand voice）。沒有對照，審查就是憑感覺。
- 標註問題不具體：改成「指出問題＋違反哪一段規範」的格式。
- 新規則直接寫進文件：改成「建議新規則，使用者核准後才寫入」。

### ⑦ Dependencies 寫清楚

**怎麼量：**

- 列出 skill 執行時用到的每一個外部東西：程式套件、CLI 工具、網站帳號、API key、檔案路徑。
- 一個一個問：名稱寫了嗎？版本有要求嗎？沒裝要怎麼裝？沒帳號要去哪裡申請？

**通過標準：**

- 每個 script 旁邊寫明用途、所需套件名稱、對應安裝指令。
- 每個外部工具寫明要不要帳號、要不要付費方案、去哪裡取得。
- 不要假設工具已經裝好。只寫「使用 PDF library」不夠，要寫明是哪個套件、如何安裝。

**不通過怎麼改：**

- 寫了工具名稱，沒寫安裝方式：補上安裝指令。不知道指令就去查，查到再寫，不要空著。
- 寫了「使用某某工具」，沒說是哪一個：寫明具體名稱。套件有全名就寫全名。
- 假設使用者已經裝好：補上「檢查是否已安裝 → 缺少時依指令安裝」這兩步。

## 常見不合格模式對照表

審查時最常看到的問題。看到左邊的樣子，先對右邊的改法：

| 不合格模式 | 問題在哪 | 改法 |
|---|---|---|
| 800 行的 SKILL.md，沒有目錄 | 模型讀不到後面，重要規則被漏讀 | 拆成主檔＋reference，主檔 500 行內，長檔加目錄 |
| 目錄寫「第三節：檢查」，標題寫「檢查與修正」 | 目錄對不上標題，模型找不到段落 | 兩邊統一，一字不差 |
| 「刪除資料前請三思」 | 高風險步驟只用文字提醒 | 改成固定 script 或寫死操作順序 |
| 每一步都寫「必須照以下五步執行」 | 低風險步驟綁太死，模型沒有判斷空間 | 低風險步驟改成目標描述，做法可以換 |
| 只在 Sonnet 上測過 | 換 Haiku 就漏步驟，換 Opus 就過度解釋 | 三個模型都測，結果寫進 front matter |
| SKILL.md → 進階.md → 細節.md | 兩層跳轉，底層內容可能只被預覽 | 底層連結拉到主檔，全部一層直達 |
| checklist 只有勾選框 | 失敗時不知道回哪一步，擋不住跳步 | 每份 checklist 補回返路徑 |
| 寫完就定稿 | 沒有審查，沒有修正循環 | 補上起草 → 審查 → 修訂 → 再審查 |
| 「使用 PDF library 處理檔案」 | 沒說哪個套件、怎麼裝 | 寫明套件名稱與安裝指令 |
| 規則是模型自己加的 | 規範被擅自改寫 | 新規則先建議，使用者核准後才寫入 |

## 審查報告輸出格式

審查完，輸出一份報告。格式固定，不要自由發揮：

```markdown
# 審查報告：<skill 名稱>

- 審查日期：<YYYY-MM-DD>
- 主檔行數：<數字> 行
- reference 檔案：<數量> 個，各 <行數> 行
- 測試任務：<任務描述>
- 測試模型：Haiku / Opus / Sonnet

**逐項結果**

| 項次 | 檢查項目 | 結果 | 問題 |
|---|---|---|---|
| ① | 長檔案有目錄 | 通過／不通過 | <一句話> |
| ② | 自由度有分層 | 通過／不通過 | <一句話> |
| ③ | 逐個模型測試 | 通過／不通過 | <一句話> |
| ④ | references 只放一層 | 通過／不通過 | <一句話> |
| ⑤ | checklist 能阻止跳步 | 通過／不通過 | <一句話> |
| ⑥ | 自我修正循環 | 通過／不通過 | <一句話> |
| ⑦ | dependencies 寫清楚 | 通過／不通過 | <一句話> |

**修正建議（依優先順序）**

1. <最嚴重的問題，先改這個>
2. <第二個問題>
3. <第三個問題>

**下一步**

- 修正後再跑一次審查，7 項都通過才算完成。
```

## 審查流程 checklist

照這個順序跑。任何一步失敗，回到指定的步驟，不要跳過去：

- [ ] 備齊目標 skill 的 SKILL.md 和所有 reference 檔案
  - 失敗 → 回到「審查前先準備」，檔案沒齊不要開始審
- [ ] 量出每一份檔案的行數，超過 100 行的檢查目錄
  - 失敗 → 回到第 ① 項，目錄補好再往下
- [ ] 每個步驟標出自由度，高風險步驟確認有固定 script
  - 失敗 → 回到第 ② 項，分層寫清楚再往下
- [ ] 用真實任務在 Haiku、Opus、Sonnet 上各跑一次
  - 失敗 → 回到第 ③ 項，測完三個模型再往下
- [ ] 畫出引用關係圖，確認全部一層直達，主檔 500 行內
  - 失敗 → 回到第 ④ 項，拆分或拉平連結再往下
- [ ] 檢查每一份 checklist 有回返路徑和驗證項
  - 失敗 → 回到第 ⑤ 項，補上回返路徑再往下
- [ ] 確認有四步自我修正循環，規則改善需使用者核准
  - 失敗 → 回到第 ⑥ 項，補上循環再往下
- [ ] 列出所有 dependencies，名稱與安裝指令齊全
  - 失敗 → 回到第 ⑦ 項，補齊再往下
- [ ] 輸出審查報告，7 項結果與修正建議都寫上
  - 7 項都通過 → 審查完成
  - 有任何一項不通過 → 修正後重新跑一次，從第 ① 項開始

## Dependencies

這個 skill 本身需要：

| 項目 | 用途 | 取得方式 |
|---|---|---|
| 終端機（或編輯器的行數顯示） | 量行數、列標題 | 系統內建。行數用 `wc -l`，標題用 `grep '^#'` |
| 目標 skill 的 SKILL.md 與 reference 檔案 | 審查對象 | 使用者提供路徑 |
| 三個模型的使用權限 | 第 ③ 項逐模型測試 | Claude Code 內建 Haiku / Opus / Sonnet；若只能用其中一個，在報告註明「只測了 Sonnet」 |
| 規範文件（style guide 或 brand voice） | 第 ⑥ 項審查對照 | 使用者提供；沒有就先寫一份，或跳過第 ⑥ 項並在報告註明 |

注意：這個 skill 不需要任何額外套件。`wc` 和 `grep` 是系統內建工具，不用安裝。

## 測試狀態

- 2026-11-20：本 skill 尚未在 Haiku / Opus / Sonnet 上逐一實測。實測後會把結果寫進這裡（預期搭配哪個模型、哪個模型表現怎樣）。
